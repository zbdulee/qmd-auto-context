# Setup and preserving upgrade

Users can ask “이 프로젝트 auto-context 설치 상태 보여줘”, “설치 준비해줘”, “검증된 준비를 적용해줘”, or “직전 적용을 되돌려줘”. Always name the project root and show the result of each phase.

1. Install this host plugin through its marketplace before using this skill. Plugin registration and hook trust are separate host actions; this skill never changes them. Resolve `ROOT` from a verified host plugin-root variable (`CLAUDE_PLUGIN_ROOT` or `PLUGIN_ROOT`), or from the absolute path of this `SKILL.md` by ascending two directories. Verify `ROOT/core/install_update.py` exists. Never infer the plugin root from the target project git root; keep it distinct from `PROJECT_ROOT`. Do not use a global install script.
2. Plugin installation has no documented Codex or Claude install callback that runs a long migration. On the first SessionStart for a project that needs setup, the plugin gives one short local notice. New hook and worker code keeps that project inactive until explicit setup succeeds; existing settings, QMD DB, wiki, and model files stay in place. This does not disable the plugin in the host or revoke hook trust. Ask the user once to run this setup skill after host marketplace install and official hook trust review. On a later plugin update, run the read-only `python3 "$ROOT/core/setup_entry.py" check-update --project "$PROJECT_ROOT"`; report the detected reasons and obtain approval before preparing or applying. SessionStart maintains an already configured project but is not an installation permission grant. A running host session that loaded an older plugin may continue using that older code until the host reloads it.
3. Run `python3 "$ROOT/core/setup_entry.py" inspect --project "$PROJECT_ROOT"`, then `plan --project "$PROJECT_ROOT"` with the required explicit options. The CLI discovers modern/legacy settings, project QMD paths, selected DB, wiki and available Node/npm. It builds the strict request itself; never author request JSON. `--qmd-mode auto` uses a verified active runtime or probes the selected existing package. If needed, supply the reviewed absolute `--qmd-entry` and `--node`; choose `--qmd-mode install` with `--npm` only after explaining package/download/native lifecycle scope, and pass both `--approve-package-execution` and `--approve-lifecycle-scripts` only with explicit authorization. Managed QMD accepts Node 22/24 LTS and Node 26 Current; guide Node 20 users to a supported version. On unsupported macOS architecture or Linux, report the managed-platform blocker and manual global-QMD fallback. Laya defaults to `--laya-mode defer`. Select `--laya-mode reuse` only with a reviewed `--laya-executable` and local `--laya-model-dir`; use `--laya-adapter` if the bundled adapter is unsuitable. Select `--laya-mode install` only after reviewing `--uv`, `--laya-lock`, and the local model directory; `--approve-laya-install` is a separate execution gate. An installed Laya runtime is not a reason to activate learning or select a private checkpoint.
4. Shadow migration is the default. The CLI requires an opted-in, published v2 wiki, an enabled wiki collection, a project-local QMD config, a model cache, and a known target model/dimension. Supply absolute `--qmd-config`, `--model-cache`, or `--source-index` when discovery cannot resolve them; use `--expected-model` or `--expected-dimension` if the target cannot be proved from config and compatible source DB. `--approve-index-execution` permits only the reviewed inactive QMD update/embed probe. If v1 cards exist, obtain a separately reviewed, owner-private `--reviewed-v2-mappings` list with verified published replacements. Do not invent wiki text, semantic mappings, model quality, or proof. If v2 wiki is missing in a project with existing settings, source DB, or wiki data, stop and report that separate wiki generation/review must finish first. For a genuinely new modern opted-in project with an empty wiki and no legacy settings or project DB, explicitly use `--bootstrap-empty-wiki --expected-dimension <reviewed dimension> --approve-index-execution` with the normal project-local config/cache. The CLI refuses an existing project-local DB even at a custom `INDEX_PATH` or project-local default cache route, and checks that route again during prepare and immediately before cutover. An existing shared global DB is accepted only if its collection paths prove that it does not cover this project. The CLI also refuses an explicit source index or any existing wiki Markdown in this mode. It verifies the embedding model with a temporary synthetic probe in the inactive generation, removes all probe documents/vectors, and activates an empty project DB; the next normal hook can create, verify, publish, and index the first real card. State `v2_empty_bootstrap` rather than claiming a completed wiki migration. `--index-mode none` can prepare only runtime/config; show its `runtime_only_no_v2_index` scope and do not call it a completed v2 migration.
5. On an explicit prepare request, rerun the same options with `python3 "$ROOT/core/setup_entry.py" prepare --project "$PROJECT_ROOT" ...`. It creates a private deterministic request file, the coordinator journal and inactive generations. Repeating identical options resumes; a changed request follows the coordinator's archive/review rules. On a separate explicit apply request, run `activate --project "$PROJECT_ROOT"` only after `prepared` and source/proof checks. Return selected QMD/index/Laya modes and daemon identity. Report `rolled_back_after_activation_failure` or `recovery_required` exactly if handoff fails.
6. On an explicit rollback request, run `rollback --project "$PROJECT_ROOT"`. Confirm pointer/settings restoration and report concurrent changes that block safe rollback.

The `update` skill refreshes an already configured index; it does not replace this setup flow. Never activate a teacher, private checkpoint, or operating plugin hook as a side effect of preparing a runtime. Private model quality/learning activation requires its separate policy and review.
