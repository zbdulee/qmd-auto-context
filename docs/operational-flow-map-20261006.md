# QMD 네 흐름의 코드 기준 동작 지도 (2026-10-06 개발본)

이 문서는 현재 설치된 0.35.2 계열의 일반 wiki 경로, 이 작업 트리의 v2 격리 경로, 아직 활성화되지 않은 연결을 구분한다. 합성 시험의 성공은 운영 프로젝트 활성화가 아니다. 비공개 원문에 대한 새 모델 호출은 이 문서 작성에 포함되지 않는다.

**S-02 연결 상태.** `core/qmd_installer.py`와 lockfile은 신규 QMD 2.5.3을 공식 lock으로 관리형 비활성 세대에 실제 설치했고, 격리 합성 DB의 collection add/update/embed/query smoke가 통과했다. 운영 active pointer는 그대로다. 명시적 프로젝트 shadow-index pointer가 있으면 `recall.py`는 전역 daemon 대신 선택된 DB/config/cache를 사용하는 로컬 QMD CLI를 호출한다. `update.sh`, SessionStart update worker, `backend/index_worker.sh`도 같은 프로젝트 pointer를 따른다. pointer가 손상되면 전역 DB로 우회하지 않는다. 합성 E2E에서만 활성화·rollback했고 실제 프로젝트나 plugin hook은 활성화하지 않았다. 자세한 설치기·네이티브 의존성 및 검증 범위는 [`qmd-installer-scope-20261006.md`](qmd-installer-scope-20261006.md)를 참조한다.

**설치 조정기 개발 상태.** `skills/setup/SKILL.md`는 host plugin 등록 후 자연어 설치 요청을 `core/setup_entry.py`의 읽기 전용 조사·업데이트 확인·결정적 계획과 자동 생성 요청의 비활성 준비, 명시적 적용, rollback으로 연결한다. 설치 자체를 실행하는 Codex/Claude host 이벤트는 문서화되어 있지 않으므로 최초 setup은 1회 명시 호출이다. 합성 fixture는 v2 wiki 부재에서 준비 차단, 패키지 실행 승인 게이트, JSON 수작업 없는 runtime-only 및 검수된 v1→v2 shadow DB 준비·적용·rollback을 확인했다. 원장이 있는 동안 기존 SessionStart 자동 설정 이주는 레거시 원본을 이동하지 않는다. v1 카드의 검증된 v2 대응 관계가 없으면 적용하지 않으며, 새 대응 카드가 생긴 뒤 shadow DB를 다시 만든다. 실제 운영 pointer·학습 정책은 바꾸지 않았다. [`install-update-contract-20261006.md`](install-update-contract-20261006.md)에 정확한 요청 필드와 미검증 범위를 적었다.

**INSTALL-REVIEW-1 보완.** `core/install_update.py`는 완료된 설치 원장을 개인 이력으로 보존하고 다음 검토 요청을 새 트랜잭션으로 시작한다. QMD root는 실제 hook/daemon resolver의 기본 관리형 root로 제한한다. legacy 설정은 기록된 intent 뒤 완성된 바이트만 원자 링크로 게시하며 중단 뒤 재개·rollback한다. shadow cutover 전에 정확한 wiki collection·파일 SHA·모델 벡터·v2 source revision·QMD config를 준비 시와 적용 직전에 다시 비교한다. 기존 관리형 daemon이 실행 중이면 QMD pointer 전환 뒤 재시작·프로세스 entry 검증을 하고 rollback 시 이전 entry로 되돌린다. Codex `hooks-codex.json`과 Claude `hooks.json`은 같은 프로젝트 원장·DB·SessionStart queue에 각자의 engine label로 들어간다. 두 host의 manifest/dispatcher/opt-in/out/동시 호출은 합성 fixture로 검증했고, 실제 Claude CLI는 이 환경에 없다. 기존 비활성 QMD native 설치 및 실제 Codex worker 생존은 하위 모듈 증거이며 새 조정기 host 통합 시험으로 소급하지 않는다.

**REVIEW-3 runtime 결속.** `core/qmd_route.py`가 관리형 실행 파일/Node/JS entry와 프로젝트 DB/config/cache를 함께 해석한다. 활성 프로젝트 index pointer가 있으면 recall·update·publisher·학습 지문이 그 선택을 따른다. v2 publisher는 상충하는 기존 DB 환경값을 거부한다. 학습 corpus fingerprint는 선택 generation도 포함하며, topical worker는 잠금 보유 중 새 job을 재스캔하고 잠금 해제 직후 남은 job을 다시 깨운다. 네 경계는 합성 fixture로만 검증했다.

**dirty queue 복구 경계.** `core/dirty_queue.py`의 enqueue와 `core/dirty_queue_claim.py`의 claim/ack는 고정 sidecar 파일의 `fcntl` 잠금을 공유한다. worker는 원본 queue를 유지한 채 소유자 전용 claim을 완성·fsync한 뒤 QMD collection add/update/embed를 실행한다. 모든 단계가 성공해야 원본의 그 prefix만 원자적으로 제거하므로, 새 enqueue는 뒤에 남는다. 실패·SIGKILL은 claim과 원본을 보존하고 다음 worker가 재시도한다. 성공 ack의 중간 중단은 완료 표시와 queue inode로 복구한다. 합성 readonly/실패/kill/동시 enqueue 회귀이며 실제 운영 queue는 변경하지 않았다.

**REVIEW3-CURRENT reload 복구.** embed/delete 뒤 daemon reload가 실패하면 claim의 `reloadRequired`가 유지된다. 다음 worker에서 QMD incremental 출력이 0/0이어도 이 의무를 다시 수행하고, reload 성공 뒤에만 flag를 지우고 ACK한다. 혼합 project/global queue도 global daemon 의무를 claim에 기록한다. 합성 실패·재기동·동시 enqueue 회귀로 확인했으며 운영 daemon에는 적용하지 않았다.

**코드 갱신과 기존 프로젝트.** 새 코드의 첫 hook은 `core/setup_guard.py`로 기존 설정과 project DB pointer/설치 원장을 읽는다. legacy 설정·미선택 DB·진행 중 원장은 내부 `setup_required`가 되어 recall·편집 hook·기존 update/topical/dirty worker가 작업을 보존하고 중지한다. SessionStart는 owner-private 버전/notice 상태에 근거해 짧은 setup skill 안내를 한 번 표시한다. 별도 명시 setup이 준비·적용에 성공하면 새 코드가 재개하고 optout은 유지된다. 호스트의 plugin enabled/trust 설정은 바꾸지 않으며, 이미 이전 코드를 메모리에 올린 세션까지 정지시킬 수는 없다. 합성 Codex·Claude 라벨과 기존 job에서 확인했고 실제 새 plugin host 수명 시험은 미검증이다.

**설치 전환의 동시성 경계.** 관리형 wiki publish·retire와 프로젝트 shadow DB 전환은 동일한 `.topical-publish.lock`을 사용한다. 조정기는 그 잠금 안에서 corpus/DB를 전환 직전과 전환 후 재확인하고, 수동 편집 경합이 검출되면 포인터를 rollback한다. 살아 있으나 health 실패인 daemon PID도 reload 대상으로 기록하며, 새 세대의 health·JS entry·Node·PID를 확인한다. QMD probe 또는 reload timeout은 JSON 실패와 rollback/recovery 상태로 반환한다.

## 1. DB 적재와 wiki 생성·수정·삭제

**현재 일반 경로.** Codex manifest [`hooks/hooks-codex.json`](../hooks/hooks-codex.json)은 `apply_patch|Edit|Write`의 `PostToolUse`에 posttool·index·compile을 각각 등록한다. 같은 이벤트의 command hook 간 완료 순서는 보장하지 않는다. `core/wiki_compile_enqueue.py`는 config의 collection role·compile trigger·안전 경로를 검사한 뒤 큐에 넣고, `hooks/run-hook`이 backend manager를 통해 one-shot compile worker를 kick한다. `compile.mode` 기본값은 `off`; 권장 온보딩 또는 명시적인 `--enable-compile`이 켤 수 있다. `core/wiki_compile_worker.py`가 extractor를 골라 생성하고 `core/wiki_verify_worker.py`가 별도 검수해 pass만 `status: verified`로 찍는다. 생성 전후 유사 wiki 검색 및 중복 판정은 `wiki_dedup_judge.py`의 설정·예산·후보 가용성에 좌우되며, 모든 의미 충돌을 자동 해결한다고 보장하지 않는다. 기본 `semanticDedup.enabled=true`, judge enabled=true, `compile.budget.extractorPerRun=10`, `cardsPerSource=10`, `verifyPerRun=3`, `dedupPairsPerCompile=1`, `dedupPairsPerScan=8`이다(`core/config.py`). 무료 후보 검색과 유료 judge는 다르며, 유료 호출의 실제 제공자 청구액 상한은 아니다.

**수정·삭제.** `core/wiki_freshness.py`/`core/recall.py`는 카드의 `sourceRevisions` SHA와 현재 원문을 대조해 바뀐 카드의 주입을 막는다. `core/wiki_source_scan.py`는 SessionStart에 누락 원문을 순환 검사하고 `core/wiki_source_missing.py`가 원본 소실을 집계한다. 원문 자체를 자동 수정하지 않는다. 일반 경로의 누락 source 재지정은 사람 확인이 필요한 `wiki-source-repair` 작업이다. 새 v2 격리 코드 `core/wiki_topical_reconcile.py`의 `_projection`, `_scan`, `reconcile`, `safe_projection`은 **모든 카드의 sourceRevisions**를 역으로 보아 한 원문이 바뀌면 이를 인용하는 단일·다중 출처 카드의 해당 근거를 pending으로, 카드 전체를 주입 제외로 둔다. `PostToolUse` 힌트는 빠르게 차단만 하고, `Stop`의 독립 worker에서 최종 파일 SHA를 다시 읽고, 중단 시 다음 SessionStart에서 복구해 create→delete 등 한 턴의 변경을 합친다. `apply_patch`의 `*** Add/Update/Delete File`, `*** Move to` 헤더를 대상으로 하되 OS나 shell에서 발생한 모든 삭제·개명을 즉시 포착하는 것은 아니다. `posttool.py`의 편집 직후 검색 입력에는 추가된 줄만 넣고 삭제만 있는 patch에서는 새 검색을 유발하지 않는다. 격리 `wiki_topical_refresh.py`는 명시적 backend runner로 다중 출처 카드에서 삭제된 출처를 뺀 새 카드를 생성·검증·게시·QMD 동기화한다. 모든 출처가 삭제되면 이전 카드를 격리 archive로 옮기고 QMD에서 비활성화한다. completed 응답 및 게시/index 단계는 private journal에 기록하며 중단되면 다음 격리 SessionStart 일회성 worker가 재사용한다. uncertain 외부 호출과 추가 의미 검토가 필요한 경우에는 더 호출하지 않고 pending_review로 남긴다. 원자적 파일 게시와 SQLite 색인은 별도 단계이므로 중간 상태의 stale 결과는 recall이 제외한다. 실제 QMD CLI/SQLite와 합성 원문 테스트가 이를 확인했으며, 이 orchestrator는 한 카드씩만 갱신한다.

**엔진.** 일반 compile 생성·검수는 `compile.extractor.builtins/backends`와 `compile.verify.builtins/crossEngine`으로 선택한다. Claude/Sonnet 또는 Codex 같은 host/model 선택은 설치된 host CLI와 명시 설정에 의존한다. Luna는 현재 이 저장소의 extractor 모델 선택지로 증명되지 않았다. `core/context_learning/teacher_budget.py`의 teacher/review 예산은 별도의 선택적 라벨링 경로다. 이번 적재 경로가 teacher를 자동 호출하지 않는다. 모델을 띄우는 CLI의 plugin/skill 최소화는 `core/extractors/lib.py`의 격리 adapter 계약에 있으며, 외부 호출 허가를 뜻하지 않는다.

**v2 유사 카드 게이트.** `core/wiki_topical_similarity.py`는 생성 전 기존 카드의 lead로, 생성 후 새 카드의 lead로 격리 QMD `vsearch`를 수행한다. 검색 결과의 활성 DB hash, 실제 파일 hash, backend-pass 출처 증명을 다시 대조한다. 후보의 짧은 맥락만 생성 요청에 전달한다. 생성 후 사실·출처까지 정확히 같은 카드는 exact duplicate로 보류하고, 같은 문구라도 계획/실제·시점·조건이 다르면 차이를 표시해 보류한다. 그 외 의미 비교도 검색 점수로 결정하지 않는다. owner-only 검토 파일에서 해당 카드 쌍의 바이트 hash에 결속한 `distinct` 판정을 받기 전에는 게시하지 않는다. `duplicate`, `conflict`, `unclear`는 계속 보류하며 자동 병합·삭제하지 않는다. 이 게이트는 teacher를 호출하지 않는다. 별도 teacher 정책·예산·호출 계약이 없는 현재 상태에서는 사람 검토로만 해제할 수 있다.

**새 원문 v2 경로.** 기존 카드가 연결되지 않은 새 Markdown은 `core/wiki_topical_create.py`의 별도 원장으로 한 파일씩 처리한다. 프로젝트 opt-in, Codex extractor/verify 정책, 추정 비용 예산을 확인한 뒤 생성·검수·유사성 검토·게시·격리 QMD 색인/임베딩 순서로 진행한다. 정책이 없으면 `auto_teacher_policy_required`, 결과가 불명확한 호출이면 `generation_attempt_reserved/uncertain`으로 보류한다. 명확히 실패한 생성 호출은 예산이 30센트 이상일 때 다음 Stop 또는 SessionStart 복구 경계에서 다른 시도 ID로 한 번 더 시도한다. 진행 중 원문이 바뀌거나 삭제되면 이전 배치를 폐기하고 현재 SHA로 다음 경계에서 다시 판정한다. 기존 카드 갱신과 새 원문이 한 배치에 있으면 기존 카드를 먼저 갱신하고 새 원문은 뒤따르는 Stop worker 턴 또는 SessionStart 복구에서 처리한다. 실제 격리 QMD/SQLite와 승인된 합성 teacher CLI로만 검증했다.

## 2. 검색과 주입

**현재 운영 경로.** `UserPromptSubmit` → `hooks/run-hook recall` → `core/recall.py`가 설정된 QMD collection을 질의한다. 기본 `topN=3`, `recallStrategy=hierarchical`, `injectSummaryMaxChars=600`, `injectSourcePathsPerCard=3`, `contextLearning.candidateTopK=8`(capture 별도 opt-in)이다. wiki role 결과의 실제 파일을 열어 `verified`·compiler 소유·`sourceRevisions` 신선도·`verifiedBodyHash`를 검사하고, 본문 줄을 인용 접두로 감싸 `additionalContext`에 넣는다. 출처 경로는 후속 Read를 위한 주소이며 정확한 원문 범위 전문을 매 질의 자동 fetch하지 않는다. 0결과면 주입하지 않는다. `posttool.py`는 편집 직후 연속성 힌트를 만들 수 있지만 QMD 색인 완료를 기다리는 동기 경로가 아니다.

**편집 이벤트.** Codex manifest의 `PreToolUse`/`PostToolUse` matcher는 `apply_patch|Edit|Write`다. `posttool.py`는 `apply_patch`의 Add/Update/Delete 헤더를 해석한다. 삭제된 파일의 본문을 새 검색 입력에 넣지 않는다. `index_enqueue.py`/`wiki_compile_enqueue.py`는 자신이 지원하는 편집 경로만 큐에 넣는다. `core/wiki_topical_reconcile.py`는 v2 합성 경로에서 삭제·개명 힌트를 추적하되 최종 디스크 상태로 확정한다.

**새 v2 선택 경로.** `core/wiki_topical_publish.py`의 `publish` CLI는 backend-pass attestation 카드를 격리 wiki에 게시한 다음 해당 프로젝트만 `qmd update`/embed하고 DB의 문서 해시·벡터를 확인한다. `sync`도 모든 게시 카드의 원문 기반 검증 증명을 다시 확인한다. 합성 E2E는 실제 QMD CLI 검색 결과가 기존 recall hook에서 전체 카드 본문으로 주입되고, 원문 변경·무검증 카드가 차단됨을 보였다. `contextLearning.liveSelection: true`이면 실제 recall 경로가 QMD 최대 15개를 받아 신선한 wiki 카드의 완전한 compact 본문을 로컬 Laya adapter에 넘기고 0–3장 결과를 선택한다. QMD 활성 문서 hash와 실제 파일 hash가 다르면 선택기를 호출하지 않는다. 로컬 정책·checkpoint·corpus·응답 오류 시 기존 QMD 선택으로 돌아가며 이유를 기록한다. 합성 hook은 stub 선택과 adapter 부재 fallback을 사용했다. 별도 합성 1카드 호출은 기존 Mini Laya runtime/base head의 실제 0장 예측에 성공했다. 운영 Laya checkpoint를 이 개발 checkout에 연결하거나 실문서 추론을 수행하지 않았다. 원문 후속 Read를 강제하는 경로도 없다.

## 3. SessionStart

`hooks/hooks-codex.json`의 SessionStart에는 짧은 `update-queued`와 v2 opt-in `topical-reconcile` command가 함께 있다. 서로의 완료를 기다리는 순차 보장은 없다. `hooks/run-hook`은 맨 먼저 sandbox/headless 가드를 적용한다. `update-queued`는 프로젝트 경로만 private durable job으로 기록하고 독립 one-shot worker를 시작한다. worker가 backend ensure/warm/rotate 뒤 기존 `core/update.sh`를 실행하며, `update.sh`의 자체 worker가 collection 등록/정리 → `qmd update` → embed → dedup/orphan 처리 등을 수행한다. source missing scan도 worker 경로다. 첫 미결정 opt-in 안내 외의 기존 SessionStart 안내는 worker 로그에 기록되므로 같은 턴에 표시되지 않는 제한이 있다. opt-in `contextLearning.autoCycle`의 기본 `current`는 QMD worker의 update와 성공한 embed 뒤에만 launcher를 호출하며, worker가 생략되거나 embed 실패 시 다음 세션까지 미룬다. **due 검사·학습은 launcher의 자식 프로세스**에서 실행된다. 게이트 이전에 모델·데이터를 설치하지 않는다. 플러그인 설치만으로 private 학습을 시작하지 않는다.

신규 프로젝트는 `.auto-context/settings.json`의 명시적 opt-in이 있어야 컬렉션이 등록된다. optout·pending·risky는 일반 인덱싱을 막는다(`core/update.sh`, `core/config.py`). 누락 편집은 `core/sync.py`의 수동 스냅샷 비교 또는 SessionStart의 source scan·v2 격리 reconcile이 복구한다. `sync.py`의 변경 감지는 mtime_ns+size, 신뢰/주입 최종 판정은 source SHA-256이다. 같은 문서가 바뀌지 않았으면 QMD가 기존 문서 해시/벡터를 재사용할 수 있으나, `qmd update`와 embed를 정확히 한 번만 실행한다는 전역 보장은 하지 않는다. 기존 writer lock과 큐/해시로 경합·중복을 줄인다.

`update-queued`는 첫 미결정 opt-in 안내만 읽기 전용 resolve(1초 상한)로 같은 턴에 출력한다. 나머지 기존 안내는 worker 로그에 남는 제한이 계속 있다.

## 4. 적응형 로컬 배치 학습

기존 `core/context_learning/schedule.py:run_due_cycle`과 이번 `core/context_learning_auto.py`가 사용하는 실제 trigger는 **명시 opt-in 프로젝트의 SessionStart**다. `core/update.sh`가 비동기 one-shot을 띄우고, private `auto-cycle.json`의 고정 version ID·revision JSON·trainer argv·incumbent artifact·시간/RSS 상한을 읽는다. `learning-schedule.lock`, cycle lock, 결정적 cycle ID가 동시 세션·중단 재개를 제어한다. teacher 호출이나 상시 daemon은 없다. `core/context_learning/local_cycle.py`가 reviewed train 100건, validation 50건, evaluation 50건 이상을 요구하고, validation/evaluation 각 0장 사례 10건 이상·가족 5개 이상 및 manifest/revision 재검사를 통과해야 학습한다. train만 trainer에 전달하고 validation은 incumbent/challenger를 같은 입력에서 비교해 승격을 결정한다. evaluation은 선택 후 한 번 보고하며 승격 기준으로 사용하지 않는다. 승격은 정확 선택 개선과 necessary recall/0장 정확률/무관 주입률 비퇴행을 요구하고, private active pointer만 바꾼다.

`core/context_learning/cycle_policy.py:next_interval`의 목표는 95%이다. 기준 간격은 24시간, 상한은 14일이다. 50문항·5가족·0장 10건 이상의 고정 검증에서 Wilson 하한을 같은 표본 크기의 달성 가능 최대 하한으로 나눈 pacing 점수를 exact rate로 제한한다. 95% 이상이면 ×2, 80–95% 사이면 부드럽게 연장하고 그 이하는 ÷2한다. 새 task/document 가족·source revision 변화·최근 실패는 ÷2 쪽으로 가되 최소 24시간이다. 자료 부족은 연장하지 않고 최대 72시간이다. 정규화 점수는 실제 정확도에 대한 95% 신뢰 주장이 아니며 승격 임계값도 아니다.

**현재 자료/모집단 경계.** `contextLearning.capture`는 query·후보·기존 final 선택과 후보 당시 파일 revision SHA 및 compact body를 private DB에 기록할 수 있다. 읽기 전용 QMD active documents의 경로·해시와 검색 설정의 corpus fingerprint가 가능하면 `index_revision`에 저장된다. 지문 변화는 과거 sample을 덮어쓰지 않고 review queue에 등록하며, 현재 corpus와 다른 평가 manifest는 기본 `dataMode: current` 자동 학습에서 제외한다. `selection_queue.build_queue`는 저장된 sample·review·선택 gold와 현재 제공된 revision을 대조하고 요청/문서 가족을 분할한다. 후보 재검색·전체 본문 재검토·새 gold 승인은 사람 작업이며 자동 마이그레이션이 아니다. `historical_snapshot`은 별도 명시한 동결 자료 모드다. 색인 설정·문서 변화 감지는 capture 또는 current auto-cycle 시점에 수행된다. 운영 hook에서 자동 재라벨링하거나 model 품질을 현재 모집단으로 소급 주장하지 않는다.

설치 전환의 일반 wiki writer와 실패 경계 목록은 [`install-update-writer-error-audit-20261006.md`](install-update-writer-error-audit-20261006.md)를 따른다. 일반 compile·verify의 카드/index/log 변경과 topical 게시·퇴역이 동일 프로젝트 잠금을 공유하며, 최종 SQLite 검사 오류도 rollback/recovery JSON 경로로 반환한다.

**2026-10-07 topical 회복 경계.** Stop의 inFlight가 수정·삭제 원문을 선점했으면 다음 SessionStart의 같은 카드 refresh가 잠금 안에서 그 batch를 이어받는다. journal 작성 전 원문이 다시 바뀌면 이전 batch를 정리하고 최종 snapshot을 새로 claim한다. 검증된 새 카드를 게시하고 이전 카드를 퇴역시킨 뒤 `qmd update`/embed/cleanup을 선택된 프로젝트 DB에 실행한다. QMD cleanup은 퇴역 문서와 고아 벡터를 지운다. 마지막 문서가 지워져 모델 지문 행이 없어져도 `select_runtime`은 준비 당시 스키마·고정 config와 빈 활성 문서/벡터를 확인하고 같은 선택 DB를 유지한다. 활성 문서가 남은 지문 누락이나 다른 모델 지문은 계속 거부한다. 실제 Claude 합성 Edit/Bash 흐름과 별도 활성 shadow DB의 직접 중단 복구에서 확인했으며, 이 수정 후 Claude host 재실행은 자동 승인 검토 거부로 미검증이다.

**2026-10-07 승인된 Codex·Claude 합성 호스트 결과.** 실제 Claude CLI는 Write→Edit→Bash 삭제, 실제 Codex CLI는 `apply_patch` 생성→수정→삭제를 수행했다. 각 다음 SessionStart의 owner-only worker가 로컬 합성 teacher로 생성·검수하고 기존 오프라인 QMD 2.5.3의 격리 DB를 1문서/1벡터에서 마지막 퇴역 후 0/0으로 만들었다. Codex UserPromptSubmit은 로컬 daemon과 연결한 키워드 질의에서 검증된 본문 한 개를 주입했다. 수정 갱신 중 임시 페이지 목록이 비어도 pending source의 이전 카드 projection을 `excluded_pending_refresh`로 유지해 batch 소유권을 보존한다. 일시적 단절로 남은 Codex `qmd_synced` journal은 다음 SessionStart에서 외부 teacher 재호출 없이 완료됐다. 기록된 세션·로컬 검색·회귀 로그는 별도 합성 호스트 증거 manifest에 고정한다. 운영 프로젝트 전환과 비공개 자료 품질 검증은 이 결과의 범위 밖이다.

활성 shadow DB의 recall 어휘 게이트도 `qmd_project_query.query`로 같은 DB/config/cache를 사용한다. 전역 daemon의 어휘 결과가 선택 DB의 본문 주입을 차단하지 않도록 한다. 로컬 어휘 질의 오류는 기존 정밀도 프로브의 fail-open 규칙을 유지한다. 실제 Claude 지속 세션에서 선택 DB가 새 카드 1건을 반환하고 어휘 히트 1건·본문 주입 1건을 기록했으며, Codex 일반 세션에서도 로컬 daemon 본문 주입 1건을 확인했다.

**2026-10-07 신규 빈 프로젝트 bootstrap 경계.** `setup_entry.py`는 명시적인 `--bootstrap-empty-wiki`에서만 기존 설정·wiki·프로젝트 DB가 없는 새 opt-in 프로젝트를 허용한다. 계획 때의 index route를 요청에 보존하고 준비·적용 직전 다시 검사한다. 프로젝트 내부의 사용자 지정 `INDEX_PATH` 또는 기본 cache DB가 생기면 전환을 멈추며, 공유 전역 DB는 이 프로젝트의 collection을 포함하지 않음을 읽기 전용으로 증명해야 한다. 임시 probe로 모델/차원을 검증한 빈 shadow DB를 선택하면 일반 hook이 첫 검증 카드를 게시한다. 적용 전 중단은 새 generation 준비로 복구되고 rollback은 pointer를 제거한다.

**2026-10-07 Stop 자동 실행 보정.** 일반 호스트의 Stop hook은 payload의 프로젝트 cwd를 `setup_guard.py hook-root`로 확인하고, 명시 opt-in marker·선택 프로젝트 DB·설치 원장 상태를 통과하면 private job을 기록한다. `core/topical_hook_queue.py`의 독립 worker는 같은 Stop 작업에서 최종 원문 스캔→batch claim→승인된 `.topical-auto-refresh.json`의 sourceRoots/teacher/예산을 사용한 생성·검수·게시·선택 QMD 갱신을 진행한다. SessionStart는 실패·중단된 job과 journal을 다시 깨우는 복구 경계다. 승인된 정책이 없으면 외부 teacher 호출은 보류된다. 합성 Claude 실제 호스트의 Write→Edit→Bash 삭제는 각 Stop만으로 0→1→1→0 문서/벡터를 만들었고, 첫 생성 worker는 호스트 종료 뒤에도 완료했다. 이 검증은 운영 자료와 운영 DB를 사용하지 않았다.

Codex CLI 최신 합성 실행은 파일 생성까지 확인됐지만 해당 세션에서 Stop hook 실행이 관측되지 않았다. 동일 파일을 `topical-stop codex` 로컬 dispatcher에 전달한 결과는 게시·선택 DB 1/1로 완료됐다. 이 둘은 별도 증거이며 Codex 호스트 Stop 자동 등록/신뢰는 남은 검증 항목이다.

**2026-10-07 Stop 다중 작업·정책 선검사.** owner-only 자동 정책은 schema·enabled·sourceRoots·engine·compileCfg·추정 예산을 원문 scan과 batch claim 전에 전부 검사한다. `enabled:false`는 topical queue·reconcile state를 만들지 않으며 optout도 hook 입구에서 막는다. 잘못된 정책은 원문을 claim하지 않고 `pending_review` 상태로 job을 정리한다. 자동 worker는 한 Stop/복구 handoff에서 남은 생성·갱신·삭제를 계속 처리한다. 한 job은 최대 12개 작업, 각 작업의 정책상 최대 추정액 합계 640센트에서 멈추며, 남은 queue는 `stop_batch_budget_exhausted` 검토 상태로 표시한다. 유사성 판결·외부 호출 실패·정책 변경도 즉시 보류하고 단계별 journal을 보존한다. 격리 QMD와 합성 teacher 회귀는 두 신규 원문과 다음 턴의 수정 1·삭제 1·신규 2를 각각 Stop 한 번으로 완료하고, 중간 QMD 실패 뒤 같은 durable job으로 확인된 모델 결과를 재사용했다.

**2026-10-07 동일 턴 Stop 예산 경계 보정.** 12작업/640센트 상한은 job이나 원문 snapshot마다 다시 시작하지 않고 같은 `turnKey` 전체에 적용한다. `core/topical_stop_budget.py`는 snapshot별 미완료 작업 예약과 별도의 턴 전체 누계를 같은 owner-only 원장에 원자 게시·fsync한다. 중복 Stop, 원문 추가·수정·삭제, SessionStart 복구, 실패 job의 재시작, 동시 worker 모두 같은 턴 누계를 공유한다. 새 snapshot은 작업 중복과 원문 SHA 확인용이며 예산 증액 근거가 아니다. 예약은 모델 호출 전에 기록되고 실패 뒤 재시도는 동일 미완료 예약을 재사용한다. 명시적인 새 정상 턴만 새 누계를 가지며, 정책 변경은 고정 지문 불일치로 호출 전에 멈춘다. 이전 snapshot별 v1 원장은 모든 scope 예약을 합산해 v2로 이행하며 이미 상한을 넘은 턴도 비용을 잊지 않고 추가 호출을 거부한다. 위의 “job 한 개” 또는 “새 snapshot의 새 예산” 표현보다 이 턴 전체 경계가 우선한다.

예산을 전부 예약한 뒤 동일 Stop이 다시 오더라도 queue·inFlight·journal이 모두 비어 있으면 작업과 새 예약 없이 `no_net_changes`로 끝난다. queue가 비어 있어도 완료된 batch와 일치하는 journal 정리만 필요하면 모델 호출 없이 정리하고 예약을 늘리지 않는다. 완료 batch와 journal이 다르면 자동 정리를 거부한다.

오래된 턴의 지연 중복 Stop은 새 snapshot scope를 보더라도 더 최근 정상 턴의 SessionStart 복구 포인터를 빼앗지 않는다. 복구는 마지막 정상 턴의 누계를 이어받고, 옛 턴의 640센트 상한은 독립적으로 유지된다.

**2026-10-07 장기 실행 원장 v3 보정.** 위 턴 전체 예산은 현재 단일 누적 JSON 대신 `core/topical_stop_budget.py`의 턴별 owner-only 파일로 기록한다. 런타임은 필요한 턴 파일 하나와 일정 크기의 복구 포인터만 읽는다. queue·inFlight·journal이 모두 비어 있는 Stop은 예산 잠금과 파일을 만들지 않는다. 비용을 예약한 옛 턴의 파일은 자동 삭제하지 않아 재시작과 지연 중복 Stop에서도 12작업/640센트 경계가 유지된다. 이전 v1/v2 단일 원장은 잠금 아래 검증한 뒤 비용을 쓴 턴과 미완료 예약을 이행하고, 원본 바이트를 개인 archive에 남긴 후 이전 경로를 제거한다. 이행이 중단되면 동일한 턴 파일·복구 포인터·archive를 검증하고 재개하며 충돌 또는 손상은 자동 호출을 중단한다. 합성 회귀는 무작업 Stop 9,000회에서 원장·잠금 파일 0개, 유료 정상 턴 10,000개에서 총 턴 파일 4 MiB 초과, 재시작 뒤 오래된 소진 턴 재호출 거부와 미완료 예약 재사용, 4 MiB를 넘는 유효 v2 원장의 중단 이행 재개를 검증한다. 실제 Codex host Stop은 이 수정본의 독립 재검토, 공식 캐시 설치, 사용자 훅 직접 신뢰 후 검증 대상으로 남는다.

기존 원장 이행 중 한 유료 턴에 비용 0인 snapshot scope가 수백 개 쌓인 경우에는 예약도 미완료 작업도 없는 scope를 압축한다. 다른 정책 지문이 있었으면 그 대표 scope 하나를 남겨 `mixed_legacy_policy` 차단을 보존하고, 활성 snapshot은 별도 복구 포인터에 둔다. 이전 v3 이행이 압축 전 턴 파일을 게시하고 중단된 경우에는 그 파일의 모든 scope·예약을 원본과 비교한 뒤 원자적으로 압축해 재개한다. Python 3.9 합성 회귀는 유료 턴의 무예약 scope 249개, 혼합 정책, 이전 파일 게시 후 중단, 재시작 뒤 기존 비용·정책 차단을 확인한다.
