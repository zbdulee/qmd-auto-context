# Managed setup and preserving update contract (development)

## User entry

After installing the host plugin from its marketplace, ask the agent: “Show the auto-context setup plan for this project,” “Prepare the reviewed setup in isolation,” “Apply the prepared setup,” or “Roll back the last setup.” The exposed `setup` skill invokes `core/install_update.py` and shows its JSON status. The existing `update` skill remains the index refresh command; it does not install packages.

The maintenance CLI is `python3 core/install_update.py inspect|prepare|activate|status|rollback --project <absolute project path>`. `prepare` also takes a reviewed JSON request file. No hook installs a runtime, changes a pointer, or calls an external model automatically. The host marketplace installation remains a separate, explicit host action.

## Supported execution and requests

The bundled managed QMD/Laya installation lock and default runtime roots target macOS arm64. Managed QMD accepts Node 22 and 24 LTS, and Node 26 Current as a test target; Node 20 is end of life and is rejected by installer preflight and runtime reuse. Upgrade a Node 20 installation to Node 22 or 24 LTS before preparing managed QMD. Node 26 passes the synthetic version gate and is included in the CI matrix, but its native QMD modules still require an actual Node 26 probe before compatibility can be claimed. Odd major versions are outside this support policy. Laya uses a separate Python 3.12.14 generation, and Python >=3.9 is required for the plugin hook. Other OS/architecture combinations remain supported only by the existing, explicitly installed global QMD hook path; managed setup reports `unsupported_managed_platform` with manual guidance and makes no changes. QMD runtime reuse requires an exact, proved 2.5.3 package; other globally installed QMD versions are inventoried but never overwritten. The normal backend accepts `>=2.5.3 <3`, which is a wider policy than the managed installer.

A strict JSON request chooses `qmd.mode` (`active`, `reuse`, or `install`), `laya.mode` (`defer`, `active`, `reuse`, or `install`), and `index.mode` (`none` or `shadow`). It names every external executable/model/cache explicitly and includes installation execution gates for new packages. `reuse` validates the existing installation; `install` uses the checked-in hash locks and creates an inactive generation. `shadow` stages a new project DB against the existing wiki and model cache. The request records a project root and explicit `runtimeRoots.qmd`/`runtimeRoots.laya` paths. `runtimeRoots.qmd` must equal the default managed root reported by `inspect`; the hook and daemon resolver use that same root. `inspect` reports default roots and Node/npm candidates without executing them. The coordinator refuses a different project or changed request on resume, except a reviewed wiki mapping submitted while `awaiting_legacy_review`; that transition rebuilds the shadow index before cutover. The CLI does not infer permission from the presence of a package or a model cache.

## Request shape

The reviewed JSON request uses `schema: "qmd-install-request-v1"` and an absolute `project`. It requires:

| Field | Choices and required inputs |
|---|---|
| `runtimeRoots` | Absolute owner-private roots. `qmd` must be `inspect.defaultRuntimeRoots.qmd`; `laya` is explicitly chosen. |
| `qmd` | `active`; `reuse` with absolute `qmd` and `node`; or `install` with absolute `node` and `npm`, boolean `allowExecution` and `allowLifecycleScripts`. |
| `laya` | `defer`; `active`; `reuse` with absolute `executable`, `adapter`, and `modelDir`; or `install` with absolute `uv`, `lock`, `adapter`, and `modelDir`, `uvSha256`, `lockSha256`, and boolean `allowExecution`. |
| `index` | `none`; or `shadow` with absolute `config`, `wikiDir`, and `modelCache`, `sourceIndex` as an absolute path or null, `expectedModel`, positive `expectedDimension`, and boolean `allowExecution`. |
| `config` | `preserve` or `copy_legacy`. Copy retains the legacy source. |
| `wiki` | `preserve`; or `reviewed_v2` with a complete `mappings` array. Each row has `legacyPath`, `legacySha256`, `generationId`, and `cardId`. |

The `install` gates approve package execution only when explicitly set in a reviewed request. `shadow` builds a new DB in a private generation; `sourceIndex` is the original DB whose consistent SQLite backup snapshot, including committed WAL pages, is frozen for rollback proof. A main-file SHA alone is insufficient for live WAL and is not used as the source drift decision. The requested QMD config must bind the one enabled wiki collection to the exact `.auto-context/wiki` directory. Each wiki Markdown file must appear as an active document with the same SHA-256 and expected-model vector. Published v2 pages and source revisions must still pass proof. The entire corpus, DB and config are checked again immediately before cutover and after all pointer and daemon steps. Source fingerprint checks never issue a checkpoint or write to the original DB. During pointer selection or return to the original index, a short SQLite `BEGIN IMMEDIATE` reservation blocks concurrent SQLite writers; it is always rolled back without DML. If the reservation cannot be obtained or the source snapshot changes, cutover fails closed. SQLite may create WAL shared-memory sidecars when taking this reservation on a checkpointed WAL file; this is the database engine's lock state, not a content migration. The coordinator holds the same owner-private project lock as managed wiki publication and retirement through validation, pointer cutover, and journal commit. An uncoordinated manual edit detected after pointer selection triggers rollback rather than `activated`. Every legacy card requires a verified, published v2 mapping before cutover. The original card remains in place.

Source fingerprint backup staging is under the process temporary directory as `qmd-source-snapshots-v1-<uid>/job-<random-128-bit-token>/snapshot.sqlite`. The root and each job are owner-only mode 0700; the snapshot, owner stamp and advisory lock files are created mode 0600. SQLite may briefly create journal or WAL sidecars inside that private job. The job lock is held from before backup creation until the snapshot is hashed and removed. Normal completion removes the whole job. On the next fingerprint entry, unlocked jobs with a matching owner stamp, expected file names, regular single-link files and owner UID are removed immediately; no age-based deletion is used, so concurrent live jobs remain intact. Unrecognized files, symlinks, hard links, malformed jobs and unsafe staging roots are preserved for manual review. A crash can therefore leave a full private backup until the next entry; there is no background sweeper. An in-memory SQLite backup was considered, but would require memory proportional to the full index and an additional serialized copy for hashing. The private disk staging keeps peak memory bounded. These backups never intentionally write or checkpoint the source DB. The cutover reservation can still create source `-wal`/`-shm` sidecars, so source logical preservation is not a promise of zero filesystem writes.

## Phase and recovery rules

1. `inspect` reads current host/runtime/config/wiki/index inventory without writes. It reports unsupported platform and legacy wiki blockers; no “installed” status is inferred from plan-only code.
2. `prepare` creates an owner-private project journal, copies no user source and changes no active pointer. Each prepared generation is recorded only after the existing installer or shadow-index proof succeeds. A pending journal prevents the SessionStart legacy-config migration from moving the frozen `.auto-context.json` source. A failing step leaves the journal resumable. Repeating the same request reuses already prepared stages; changing it requires an explicit rollback/abandon review.
3. Before `activate`, the coordinator rechecks prepared proofs, original DB and settings hashes, pointer baselines, platform, and legacy wiki status. v1/missing/future wiki cards stay in their original location. Any such card blocks v2 cutover pending reviewed conversion; no automatic semantic migration or silent deletion occurs. Legacy `.auto-context.json` or `.agents/qmd-recall.json` can be copied to modern settings only after byte/normalization proof; the original stays intact. A write-ahead settings intent records the source and target hash before an atomic file link. Resume can adopt the exact completed bytes after a crash; rollback removes only a matching file.
4. `activate` selects QMD, confirms the hook/daemon resolver chooses that wrapper, then selects the project DB and Laya as separately journaled transitions. If a managed daemon process exists, including one whose health endpoint fails, it reloads through the backend manager and verifies health plus the new process entry and Node identity. A subprocess timeout enters the same structured rollback or recovery path as other activation failures. Rollback reloads the restored selection. A failed transition restores already changed pointers only if their bytes still equal what this transaction wrote. It reports `recovery_required` rather than claiming partial success if a concurrent writer prevents restoration.
5. `rollback` checks current pointer and settings hashes before restoring their pre-activation bytes, with each runtime's activation lock. It never deletes original DB, wiki, checkpoint, gold, history, or cached models. Prepared generations remain inactive for inspection; explicit cleanup is separate. Repeated `activate`/`rollback` is idempotent. Laya `reuse` records an attested external runtime without changing a managed pointer; Laya `active` keeps the existing selected pointer. Learning policy and checkpoint selection remain separate.

No actual operating pointer, global config, model cache, or user source is used by the development E2E; tests use owner-private synthetic projects and injected installer runners. This coordinator E2E made no package download or external model call and did not change user data. Package lifecycle scripts and operating project migration remain separate; actual host trust is handled by the official Codex UI.

The complete product wiki writer, lock-order, and post-cutover failure inventory is in [`install-update-writer-error-audit-20261006.md`](install-update-writer-error-audit-20261006.md). Ordinary SQLite and callback exceptions enter the same structured rollback path; interrupted processes retain write-ahead recovery state.
